# Hibernate

## Архитектура Hibernate и ключевые компоненты: SessionFactory и Session

Hibernate — это ORM-фреймворк, который стоит между вашим Java-кодом и JDBC. Чтобы понимать его поведение, нужно чётко представлять архитектуру и роль двух центральных объектов: SessionFactory и Session. Всё остальное — производные от них.

Общая архитектура (сверху вниз)
```
Application
    ↓
SessionFactory  (тяжёлый, один на приложение)
    ↓
Session         (лёгкий, один на единицу работы)
    ↓
Persistence Context (кэш первого уровня внутри Session)
    ↓
JDBC Connection / DataSource
    ↓
Database
```

И ещё сбоку: кэш второго уровня, Connection Pool, Transaction Manager, Dialect, Interceptor/Listener — всё это живёт на уровне `SessionFactory`.

### SessionFactory

`SessionFactory` — это неизменяемая, потокобезопасная, тяжеловесная фабрика, которая создаётся один раз на всё приложение (на одну базу данных). Внутри неё хранится:

* Метаданные маппинга — все сущности, их поля, связи, стратегии загрузки. Строятся один раз при старте.
* Кэш второго уровня (если включён).
* Настройки подключения — DataSource, пул соединений, Dialect.
* SQL-запросы, скомпилированные из HQL/JPQL (query plan cache).
* Слушатели событий (EventListener) — interceptors, callbacks.
* Настройки кэша запросов, batching, statistics.

**Как создаётся:**

В современном Spring Boot вы этого не делаете вручную — Spring создаёт SessionFactory (точнее, EntityManagerFactory) при старте контекста. Но понимать, что происходит, важно.

В «чистом» Hibernate:
```java
Configuration cfg = new Configuration()
    .addAnnotatedClass(User.class)
    .configure("hibernate.cfg.xml");

SessionFactory sessionFactory = cfg.buildSessionFactory();
```

`buildSessionFactory()` — дорогая операция. Она:

1. Читает все маппинги.
2. Строит метамодель.
3. Проверяет связи.
4. Создаёт пул соединений.
5. Инициализирует кэши.
6. Компилирует именованные запросы.

На старте приложения это занимает секунды, иногда десятки секунд — на больших проектах с тысячами сущностей.

**Ключевые характеристики**

| Свойство | Значение
|--|--
| Потокобезопасность | Да
| Время жизни | Всё приложение (singleton)
| Стоимость создания | Высокая
| Состояние | Неизменяемое после создания (immutable)
| Один на | Приложение × БД
| Spring-аналог | `LocalContainerEntityManagerFactoryBean`

**Типичные ошибки**
* Создавать `SessionFactory` на каждый запрос. Это катастрофа по производительности: каждый раз перестраивается вся метамодель и пул соединений.
* Держать несколько `SessionFactory` без нужды. Обычно это нужно только для multi-tenancy или работы с несколькими БД.
* Считать его «фабрикой соединений». Нет, соединениями управляет `DataSource` / Connection Pool. `SessionFactory` — фабрика сессий, а не соединений.

### Session

`Session` — это лёгкий, недолговечный, НЕ потокобезопасный объект, представляющий одну единицу работы (unit of work) с базой данных. В JPA-терминологии ему соответствует `EntityManager`.

Внутри `Session` живёт Persistence Context — кэш первого уровня, где хранятся все загруженные и управляемые сущности.

**Время жизни**
`Session` создаётся на:
* одну транзакцию (transaction-scoped) — самый частый вариант в Spring;
* один HTTP-запрос (request-scoped) — через `OpenSessionInViewFilter` (спорная практика, см. ниже);
* один пользовательский диалог (long session, редко).

В Spring Boot `Session` открывается и закрывается автоматически благодаря `@Transactional`:
```java
@Transactional
public void updateUser(Long id, String name) {
    User user = session.get(User.class, id); // session открыта
    user.setName(name);
} // session закрыта, изменения зафлашены
```

**Что делает Session**

1. Предоставляет API для работы с БД: `save`, `persist`, `merge`, `delete`, `get`, `load`, `createQuery`, `flush`.
2. Управляет Persistence Context: отслеживает все загруженные сущности, их изменения, грязные поля (dirty checking).
3. Содержит кэш первого уровня: каждый `get`/`load` сначала ищет в кэше, потом в БД.
4. Управляет транзакцией: через `Transaction` (или `EntityTransaction` в JPA).
5. Выполняет flush: синхронизирует изменения из памяти в БД.

**Ключевые характеристики**
| Свойство | Значение
|--|--
| Потокобезопасность | Нет (нельзя шарить между потоками)
| Время жизни | Одна единица работы
| Стоимость создания | Низкая (лёгкий объект)
| Состояние | Мутабельное
| Один на | Транзакцию / запрос / единицу работы

**Типичные ошибки**
* Шарить `Session` между потоками. Не потокобезопасна, приведёт к порче Persistence Context.
* Держать `Session` открытой долго. Кэш первого уровня растёт, память утекает, данные устаревают.
* Использовать `OpenSessionInView` для ленивых загрузок в контроллере. Это антипаттерн: N+1-запросы, непредсказуемое поведение, проблемы с транзакциями. Лучше явно загружать нужные данные через `JOIN FETCH` / `@EntityGraph`.


### Persistence Context — сердце Session

Это самая важная часть, которую нужно понять. `Persistence Context` — это кэш первого уровня, живущий внутри `Session`.

**Что он делает**
1. Хранит все управляемые (persistent) сущности. Загрузили `User` — он здесь.
2. Гарантирует identity. Два вызова `session.get(User.class, 1L)` в одной сессии вернут один и тот же объект (identity map).
3. Dirty checking. При `flush` Hibernate сравнивает текущее состояние сущностей с их снимком (snapshot) на момент загрузки и генерирует `UPDATE` только для изменённых полей.
4. Write-behind. `save`/`persist` не пишут сразу в БД — они регистрируют сущность, а `flush` синхронизирует всё пакетно.

**Состояния сущностей**

| Состояние | Что значит | Как попасть
|--|--|--
| Transient | Новый объект, не связан с сессией | `new User()`
| Persistent | Управляется сессией, в Persistence Context | `session.get()`, `session.persist()`, `session.merge()`
| Detached | Был persistent, но сессия закрыта или объект эвиктнут | После закрытия `Session`, `session.evict()`
| Removed | Помечен на удаление | `session.remove()`

**Пример dirty checking**
```java
@Transactional
public void doWork() {
    User u = session.get(User.class, 1L); // загружен, snapshot сохранён
    u.setName("Bob");                      // изменено в памяти
    // flush при коммите сравнит с snapshot и выполнит UPDATE
}
```

Никакого явного `session.update()` не нужно. Это главная магия Hibernate.


### Как они взаимодействуют

```
Application → SessionFactory.openSession() → Session
                  ↑                              ↓
                  │                     Persistence Context (кэш 1-го уровня)
                  │                              ↓
            (создаётся 1 раз)            JDBC Connection (из пула)
                                                 ↓
                                          Transaction
```

Порядок типичной работы:

1. Старт приложения: создаётся `SessionFactory` (один раз).
2. Запрос пользователя: открывается `Session` (на время запроса или транзакции).
3. Работа: `Session` загружает сущности в Persistence Context, отслеживает изменения.
4. Flush: при коммите или явно — изменения синхронизируются в БД.
5. Закрытие: `Session` закрывается, Persistence Context уничтожается. Сущности становятся Detached.

### Spring-специфика
В Spring Boot всё немного иначе:

1. `SessionFactory` → создаётся Spring как `EntityManagerFactory` (обычно `LocalContainerEntityManagerFactoryBean`).
2. `Session` → обёрнут в `EntityManager` и привязан к текущему потоку через `EntityManagerHolder`.
3. `@Transactional` → управляет открытием/закрытием сессии и транзакции.
4. `OpenEntityManagerInView` → держит сессию открытой до конца HTTP-запроса.

**Полезные настройки**

```properties
# Logical? Нет — физическое соединение берётся из пула
spring.jpa.properties.hibernate.connection.provider_disables_autocommit=true

# Batching — критично для производительности
spring.jpa.properties.hibernate.jdbc.batch_size=50
spring.jpa.properties.hibernate.order_inserts=true
spring.jpa.properties.hibernate.order_updates=true

# Не давать Hibernate трогать БД при старте (используйте Flyway/Liquibase)
spring.jpa.hibernate.ddl-auto=validate

# Открывать сессию в view — не использовать в проде
spring.jpa.open-in-view=false
```

### Итог

| Критерий | `SessionFactory` | `Session`
|--|--|--
| Вес | Тяжёлый | Лёгкий
| Потокобезопасность | Да | Нет
| Время жизни | Приложение | Транзакция / запрос
| Создание | Дорого | Дёшево
| Состояние | Immutable | Mutable
| Содержит | Метаданные, кэш 2-го уровня, пул | Persistence Context, кэш 1-го уровня
| Spring-аналог | `EntityManagerFactory` | `EntityManager`


1. `SessionFactory` — один на приложение, тяжёлый, потокобезопасный. Создаётся при старте, живёт до конца.
2. `Session` — один на единицу работы, лёгкий, не потокобезопасный. Открывается и закрывается на транзакцию.
3. Persistence Context — кэш первого уровня внутри `Session`. Обеспечивает identity, dirty checking, write-behind.
4. Не шарьте `Session` между потоками. Никогда.
5. Не создавайте SessionFactory на каждый запрос. Никогда.
6. `OpenSessionInView` — антипаттерн. Отключайте в проде.
7. После закрытия `Session` сущности становятся Detached. Попытка ленивой загрузки → `LazyInitializationException`.


## Жизненный цикл сущностей и Persistence Context

Это, пожалуй, самая важная тема в Hibernate. Если вы понимаете состояния сущностей и что происходит внутри Persistence Context — 80% багов с Hibernate перестают быть загадкой.

### Что такое Persistence Context

**Persistence Context** — это контейнер управляемых (managed) сущностей внутри `Session`/`EntityManager`. Его ключевые свойства:

1. Это кэш первого уровня. Все загруженные сущности живут здесь до закрытия сессии.
2. Он гарантирует identity. В рамках одной сессии `get(User.class, 1L)` дважды вернёт один и тот же Java-объект (identity map).
3. Он отслеживает изменения. При `flush` Hibernate сравнивает текущее состояние с snapshot и генерирует `UPDATE` только для изменённых полей (dirty checking).
4. Он реализует write-behind. `save`/`persist` не пишут сразу в БД — изменения накапливаются и синхронизируются при `flush`.

```java
User u1 = session.get(User.class, 1L);
User u2 = session.get(User.class, 1L);
System.out.println(u1 == u2); // true — один и тот же объект
```

Это не «оптимизация ради оптимизации». Это семантическая гарантия: в рамках одной единицы работы вы всегда работаете с одним и тем же объектом, и не получится ситуации «два объекта, оба про User с id=1, у одного name=«A», у другого name=«B»».

### Четыре состояния сущности:

### 1. Transient (Преходящий / Новый / Транзиентный)

Объект создан через `new`, но Hibernate о нём ничего не знает.

```java
User user = new User();  // Transient
user.setName("Alice");
```

Это обычный Java-объект, созданный через оператор `new`. Он никак не связан с базой данных и текущей сессией Hibernate.

* **Связь с БД:** Отсутствует. В базе нет записи, соответствующей этому объекту.
* **Идентификатор (ID):** Обычно `null` (если только вы не задали его вручную, но Hibernate это проигнорирует).
* **Отслеживание:** Hibernate не следит за изменениями его полей. Если вы измените поле и ничего не сделаете, в БД ничего не уйдет.
* **Аналогия:** Черновик документа, который вы написали у себя на столе. Он еще не зарегистрирован в архиве.

Как перевести в другое состояние:
* В **Persistent**: вызвать `session.save()` или `session.persist()`.
* В **Detached**: (напрямую почти не переводят, обычно объект сначала сохраняют, а потом закрывают сессию).

### 2. Persistent (Управляемый / Сохраненный / Персистентный)

```java
session.persist(user);   // user стал Persistent
user.setName("Bob");     // изменение отслеживается
// при flush Hibernate сгенерирует UPDATE
```

Объект находится под управлением текущей сессии (`Session`). У него есть представление в базе данных (он там сохранен или будет сохранен при `flush`).

* **Связь с БД:** Прямая. Объекту соответствует строка в таблице.
* **Идентификатор (ID):** Обязательно имеет значение (ID из БД).
* **Отслеживание:** Hibernate внимательно следит за объектом (механизм Dirty Checking). Если вы измените любое поле этого объекта, Hibernate это заметит и при следующем `flush()` автоматически сгенерирует и выполнит SQL-запрос `UPDATE`.
* **Аналогия:** Документ, который вы достали из архива, открыли в системе и редактируете. Система видит все ваши изменения и сохранит их, когда вы нажмете "Сохранить" (flush).

Как попасть в это состояние:

* Из **Transient**: `session.save()`, `session.persist()`.
* Из **Detached**: `session.update()`, `session.saveOrUpdate()`, `session.merge()`.

Как выйти из этого состояния:

* В **Detached**: закрыть сессию (`session.close()`), очистить её (`session.clear()`) или удалить объект из кэша сессии (`session.evict()`).
* В **Removed**: вызвать `session.delete()` или `session.remove()`.

### 3. Detached (Отсоединенный)

```java
session.close();
// все загруженные сущности теперь Detached
```

Объект был в состоянии Persistent (у него есть ID и он есть в БД), но потерял связь с текущей сессией (сессия была закрыта или объект был из неё извлечен).

* **Связь с БД:** Объект существует в базе данных.
* **Идентификатор (ID):** Обязательно имеет значение.
* **Отслеживание:** Hibernate не следит за ним. Если вы измените поле Detached-объекта, в БД ничего не уйдет, пока вы не "подключите" его обратно к сессии.
* **Аналогия:** Документ, который вы физически забрали из архива к себе на стол. Вы можете его читать и даже менять, но архивная система не знает об этом. Чтобы изменения попали в архив, документ нужно вернуть (сделать merge/update).

Как попасть в это состояние:

* Из **Persistent**: закрыть сессию (`session.close()`), очистить кэш (`session.clear()`), или "вытолкнуть" объект (`session.evict()`).

Как перевести в другое состояние:

* В **Persistent**: вызвать `session.update()`, `session.saveOrUpdate()` или `session.merge()` (в новой открытой сессии).

### 4. Removed (Удаленный)

```java
session.remove(user);  // Removed
// при flush → DELETE FROM users WHERE id = ?
```

Объект помечен на удаление. Он все еще связан с сессией, но "приговорен".

* **Связь с БД:** Запись в БД еще существует, но помечена на удаление.
* **Отслеживание:** При следующем `flush()` или `commit()` Hibernate сгенерирует SQL-запрос `DELETE` и удалит строку из базы данных.
* **Аналогия:** Документ, на котором поставили красный штамп "УНИЧТОЖИТЬ". Он еще лежит в системе, но в конце рабочего дня (при commit) его отправят в шредер.

Как попасть в это состояние:

Из **Persistent**: вызвать `session.delete()` или `session.remove()`.

### Итог

Самая частая ошибка новичков — попытка изменить Detached объект и ожидание, что он сам обновится в БД.

Помните: автоматически изменения в БД уходят только из состояния Persistent. Если объект стал Detached (например, вы достали его из БД в одном методе, а обновляете в другом, где сессия уже закрыта), его нужно обязательно "переподключать" через `merge()` или `update()`.

**`persist()` vs `save()`**

| | `persist()` (JPA) | `save()` (Hibernate)
|--|--|--
| Возвращает | `void` | `Serializable` (id)
| `INSERT` | Отложенный (при flush) | Может быть немедленным (если id нужен)
| Вне транзакции | Ошибка | Работает (но плохо)
| Для detached | Ошибка | Создаст новый объект (если id есть — может быть ошибка)

Используйте `persist()`, если работаете через JPA API. Это стандарт.

**`merge()` vs `update()`**

| | `merge()` (JPA) | `update()` (Hibernate)
|--|--|--
| Что делает | Загружает текущее состояние из БД, копирует в новый managed-объект, возвращает его | «Присоединяет» переданный detached-объект к сессии
| Возвращает | Управляемую копию | `void`
| Исходный объект | Остаётся detached | Становится persistent
| Если запись удалена | Создаст новую | Бросит исключение

`merge()` не делает переданный объект managed. Он возвращает другую managed-копию.

```java
User detached = ...;               // Detached
User managed = session.merge(detached);
// detached — по-прежнему Detached
// managed — Persistent
```

**`get()` vs `load()`**

| | get() | load()
|--|--|--
| Запрос к БД | Сразу | Ленивый (прокси)
| Если не найдено | `null` | `EntityNotFoundException` при обращении
| Возвращает | Реальный объект или `null` | Прокси или реальный объект

`load()` возвращает прокси — Hibernate подсовывает подкласс, который загрузит данные при первом обращении к полю (кроме id).

**`refresh()`**

Перечитывает состояние объекта из БД и перезаписывает его в памяти. Полезно, если данные могли измениться извне (другой процесс, native SQL).

```java
session.refresh(user);  // user перезагружен из БД
```

**`evict()` / `detach()`**

Удаляет объект из Persistence Context. Объект становится Detached.

```java
session.evict(user);  // user больше не managed
```

**`clear()`**

Полностью очищает Persistence Context. Все объекты становятся Detached.

```java
session.clear();  // кэш 1-го уровня пуст
```

**`flush()`**

Синхронизирует Persistence Context с БД. Не коммитит транзакцию — только выполняет `INSERT`/`UPDATE`/`DELETE`.

```java
session.flush();  // SQL выполнен, но транзакция не закоммичена
```

Когда происходит автоматический `flush`:

* Перед коммитом транзакции.
* Перед выполнением запроса, который может затронуть затрагиваемые таблицы (auto-flush).
* При явном `flush()`.
* При `session.close()` (если не было коммита — откат).


### Dirty Checking — как Hibernate узнаёт об изменениях

При загрузке сущности Hibernate сохраняет snapshot — копию всех её полей. При flush он сравнивает текущее состояние с snapshot.

```java
@Transactional
public void rename(Long id, String newName) {
    User u = session.get(User.class, id);  // snapshot сохранён
    u.setName(newName);                    // изменено в памяти
    // flush при коммите: snapshot.name != u.name → UPDATE users SET name = ?
}
```

Что это даёт:
* Не нужно вызывать `update()` — изменения подхватываются автоматически.
* Генерируется `UPDATE` только для изменённых полей (если не отключено).
* Если ничего не изменилось — `UPDATE` не выполняется вообще.

Dirty checking срабатывает при `flush`, а не при `set`. Если вы изменили поле и откатили транзакцию — изменение не попадёт в БД (это ок). Но если вы изменили поле и не закоммитили — оно останется в памяти объекта.

### Write-behind — почему save не пишет сразу

`persist()` не выполняет `INSERT` немедленно. Он регистрирует сущность в Persistence Context, а SQL генерируется при `flush`.

Зачем:
* Батчинг. Hibernate может собрать несколько `INSERT` и отправить одним пакетом (`hibernate.jdbc.batch_size`).
* Порядок операций. Hibernate сам выстраивает порядок `INSERT`/`UPDATE`/`DELETE`, чтобы не нарушить foreign keys.
* Экономия. Если транзакция откатится — `INSERT` вообще не выполнялся.

Исключение: если стратегия генерации id — `IDENTITY` (auto-increment), Hibernate вынужден выполнить `INSERT` сразу, чтобы получить сгенерированный id. Это ломает батчинг.

### Identity Map — гарантия уникальности

```java
User u1 = session.get(User.class, 1L);
User u2 = session.get(User.class, 1L);
assert u1 == u2;  // true
```

Как это работает: Persistence Context — это `Map<EntityKey, Object>`, где ключ — `(entityClass, id)`. При `get` Hibernate сначала смотрит в map. Если объект есть — возвращает его. Если нет — загружает из БД и кладёт в map.

Зачем это нужно:
* Гарантия консистентности: не будет двух разных объектов с одинаковым id.
* Производительность: повторные `get` не ходят в БД.
* Корректный dirty checking: Hibernate знает, какой именно объект отслеживать.

> identity map живёт только внутри сессии. Между сессиями — это разные объекты.

```java
// Сессия 1
User u1 = session1.get(User.class, 1L);
session1.close();

// Сессия 2
User u2 = session2.get(User.class, 1L);
assert u1 != u2;  // разные объекты, оба с id=1
```

### Типичные ошибки и подводные камни

1. `LazyInitializationException`
```java
@Transactional
public User getUser(Long id) {
    return session.get(User.class, id);  // возвращает managed
}
// сессия закрыта, user — Detached

// в контроллере:
user.getOrders().size();  // LazyInitializationException!
```

Решение: загружать нужные данные внутри транзакции (`JOIN FETCH`, `@EntityGraph`), либо использовать DTO.

2. `merge()` не делает объект managed

```java
User detached = ...;
session.merge(detached);
detached.setName("new");  // НЕ отслеживается! detached всё ещё Detached
```

Решение: работать с результатом merge():
```java
User managed = session.merge(detached);
managed.setName("new");  // отслеживается
```

3. Изменение detached-объекта без `merge()`

```java
@Transactional
public void update(User user) {  // user пришёл извне (detached)
    user.setName("new");
    // НИЧЕГО не произойдёт — user не managed
}
```

Решение: `session.merge(user)` или загрузить заново и изменить.

4. `save()` vs `persist()` с id

Если у transient-объекта уже есть id (например, присвоен вручную), `save()` может решить, что объект detached, и выполнить `UPDATE` вместо `INSERT`. `persist()` в такой ситуации бросит исключение — это безопаснее.


5. Долгая сессия → утечка памяти

Persistence Context растёт с каждой загруженной сущностью. Если сессия открыта на весь HTTP-запрос (OpenSessionInView) и загружает тысячи объектов — память утекает.

Решение: не держать сессию дольше, чем нужно; периодически `flush()` + `clear()` в пакетной обработке.

6. `flush()` не коммитит

```java
session.flush();  // SQL выполнен, но не закоммичен
// если дальше исключение — откат
```

Решение: `flush()` — для синхронизации, `commit()` — для фиксации.

7. Auto-flush перед запросом

Hibernate делает `flush` перед `createQuery()`, если запрос затрагивает таблицы с «грязными» сущностями. Это может привести к неожиданным `UPDATE` в середине метода.

Решение: понимать это поведение; при необходимости — `FlushMode.MANUAL` / `COMMIT`.

**Пример: все состояния**

```java
@Transactional
public void demo() {
    // 1. Transient
    User user = new User();
    user.setName("Alice");
    
    // 2. Transient → Persistent
    session.persist(user);
    // при flush → INSERT
    
    // 3. Persistent (managed)
    user.setName("Bob");  // dirty checking подхватит при flush
    
    // 4. Persistent → Detached
    session.evict(user);
    user.setName("Charlie");  // НЕ отслеживается
    
    // 5. Detached → Persistent (через merge)
    User managed = session.merge(user);
    // managed — Persistent, user — всё ещё Detached
    
    // 6. Persistent → Removed
    session.remove(managed);
    // при flush → DELETE
}
```

| Операция | Transient | Persistent | Detached | Removed
|--|--|--|--|--
| `persist()` | → Persistent | — | ❌ ошибка | → Persistent (иногда)
| `merge()` | → Persistent (копия) | → Persistent (копия) | → Persistent (копия) | → Persistent (копия)
| `remove()` | ❌ ошибка | → Removed | ❌ ошибка | —
| `refresh()` | ❌ ошибка | Перечитывает | ❌ ошибка | ❌ ошибка
| `evict()` | — | → Detached | — | → Detached
| `get()`/`load()` | — | Возвращает | — | —
| Dirty checking | ❌ | ✅ | ❌ | ✅ (для DELETE)
| Lazy loading | ❌ | ✅ | ❌ (LazyInitException) | ✅

**Главное**

1. Persistence Context = кэш 1-го уровня + identity map + dirty checking + write-behind. Это сердце `Session`.
2. Четыре состояния: Transient, Persistent, Detached, Removed. Переходы — через методы сессии.
3. `persist()` ≠ `save()`, `merge()` ≠ `update()`. Понимайте разницу.
4. `merge()` возвращает копию, исходный объект остаётся detached.
5. Dirty checking срабатывает при flush, а не при `set`.
6. `flush()` не коммитит — только синхронизирует.
7. После закрытия сессии объекты Detached → ленивые поля недоступны.
8. Identity map живёт только внутри сессии — между сессиями объекты разные.
9. Долгая сессия = утечка памяти. Не держите её дольше необходимого.
10. `LazyInitializationException` — симптом неправильной работы с состояниями, а не «баг Hibernate».

## Маппинг сущностей (Entity Mapping)

Маппинг сущностей — это фундамент работы с Hibernate/JPA. Он определяет, как Java-объекты связаны с таблицами базы данных.

### Базовые аннотации: с чего начинается сущность

Любой маппинг начинается с объявления класса сущностью и определения его первичного ключа.

- `@Entity`: Помечает класс как сущность, которая будет связана с таблицей в БД. Это обязательная аннотация.

- `@Table`: Позволяет явно указать имя таблицы. Если её не использовать, Hibernate возьмёт имя класса (например, для `User` таблица будет `User`).

- `@Id`: Определяет поле, которое является первичным ключом (Primary Key).

- `@GeneratedValue`: Указывает, что значение первичного ключа будет генерироваться автоматически. Стратегия `GenerationType.IDENTITY` (автоинкремент в БД) — одна из самых распространённых и простых.

- `@Column`: Используется для тонкой настройки колонки: можно задать её имя, длину, точность, запретить `null` и т.д..

Пример простой сущности:
```java
@Entity
@Table(name = "users")
public class User {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "full_name", nullable = false)
    private String name;
    
    // ... getters and setters
}
```

### Типы связей: от одного к одному до многих ко многим

В JPA существует четыре основных типа связей. Ключевой момент для понимания — это владеющая сторона (owning side). Именно на владеющей стороне определяется, как связь будет отражена в базе данных (например, в какой таблице будет внешний ключ или таблица-связка).

1. `@ManyToOne` (Многие к одному): Самая распространённая и базовая связь. Она напрямую маппится на внешний ключ в таблице. Важно: по умолчанию JPA использует для неё `FetchType.EAGER` (жадная загрузка), что почти всегда является нежелательным.

```java
@Entity
public class Book {
    // ...
    @ManyToOne(fetch = FetchType.LAZY) // Явно указываем ленивую загрузку!
    @JoinColumn(name = "publisher_id") // Имя колонки с внешним ключом
    private Publisher publisher;
}
```

2. `@OneToMany` (Один ко многим): Обратная сторона `@ManyToOne`. В JPA эта связь почти всегда двунаправленная и должна быть невладеющей. Для этого используется атрибут `mappedBy`, который указывает на поле в дочерней сущности, владеющее связью.

```java
@Entity
public class Publisher {
    // ...
    @OneToMany(mappedBy = "publisher", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<Book> books = new ArrayList<>();
}
```

3. `@OneToOne` (Один к одному): Связь, где одна запись в таблице A соответствует ровно одной записи в таблице B. Как и `@ManyToOne`, по умолчанию использует `EAGER` загрузку. Для ленивой загрузки на дочерней стороне (где находится внешний ключ) необходимо использовать `@JoinColumn`.

4. `@ManyToMany` (Многие ко многим): Требует наличия промежуточной таблицы-связки (join table). Владеющая сторона определяет эту таблицу с помощью аннотации `@JoinTable`.

```java
// Владеющая сторона
@Entity
public class Student {
    @ManyToMany
    @JoinTable(
        name = "student_course",
        joinColumns = @JoinColumn(name = "student_id"),
        inverseJoinColumns = @JoinColumn(name = "course_id")
    )
    private Set<Course> courses = new HashSet<>();
}

// Невладеющая сторона
@Entity
public class Course {
    @ManyToMany(mappedBy = "courses")
    private Set<Student> students = new HashSet<>();
}
```

###  Каскады (`CascadeType`) и `orphanRemoval`

Эти механизмы определяют, как операции над одной сущностью влияют на связанные с ней сущности.

- `CascadeType`: Определяет, какие операции (сохранение, удаление, обновление) должны «каскадно» применяться к связанным сущностям.
    - `CascadeType.PERSIST`: При сохранении родителя автоматически сохраняются и новые дочерние сущности.
    - `CascadeType.REMOVE`: При удалении родителя удаляются и все связанные дочерние сущности.
    - `CascadeType.ALL`: Применяет все операции. Используйте с осторожностью, только если дочерняя сущность не может существовать без родителя.
- `orphanRemoval = true`: Более специфичный и мощный инструмент. Он удаляет дочернюю сущность, если её «отвязали» от родителя (например, удалили из коллекции `List<Book>` у `Publisher`), даже если саму родительскую сущность не удаляют. Это идеально подходит для моделирования отношений «композиция».

### Стратегии загрузки (`FetchType`): `LAZY` vs `EAGER`

Это одна из самых критичных для производительности тем.

- `FetchType.LAZY` (Ленивая): Hibernate загружает связанную сущность только в момент первого обращения к ней. Это рекомендуемый подход по умолчанию для всех связей, особенно для коллекций (`@OneToMany`, `@ManyToMany`), так как он предотвращает проблему N+1 и избыточную загрузку данных.
- `FetchType.EAGER `(Жадная): Hibernate загружает связанную сущность немедленно, вместе с родительской. Это может показаться удобным, но на практике часто ведёт к загрузке огромного объёма ненужных данных и проблемам с производительностью.

Главное правило: Явно указывайте `fetch = FetchType.LAZY` для всех связей `@ManyToOne` и `@OneToOne`, так как для них `EAGER` является значением по умолчанию.

### Лучшие практики и типичные ошибки

1. Всегда используйте `FetchType.LAZY` для `@ManyToOne` и `@OneToOne`. Это самое важное правило для избежания проблем с производительностью.
2. Правильно определяйте владеющую сторону. Для `@OneToMany` используйте `mappedBy` на стороне «один», а `@JoinColumn` — на стороне «многие» (владеющей).
3. Будьте осторожны с `CascadeType.ALL`. Применяйте его только для настоящих композиций, где дочерний объект не имеет смысла без родительского.
4. Используйте `orphanRemoval = true` для чистого удаления дочерних сущностей при их удалении из коллекции.
5. Не забывайте про `@JsonIgnoreProperties` при сериализации двунаправленных связей в JSON, чтобы избежать бесконечной рекурсии.
6. Для загрузки ленивых связей используйте `JOIN FETCH` или `@EntityGraph`, а не полагайтесь на `OpenSessionInView`, который считается антипаттерном.


## Языки запросов (Querying)

Глава про языки запросов — это то место, где Hibernate перестаёт быть просто «магией» и становится управляемым инструментом. Здесь важно понять три подхода и их границы: HQL/JPQL (декларативный, объектный), Criteria API (программный, типобезопасный) и Native SQL (прямой доступ к БД). В Spring-проектах над этим стоит ещё один слой — Spring Data JPA, который меняет то, как вы пишете 90% запросов.

### HQL и JPQL: объектный SQL

HQL — это собственный язык Hibernate, а JPQL — стандарт JPA, который был вдохновлён ранним HQL. Важно знать соотношение: HQL является надмножеством JPQL. Любой валидный JPQL-запрос — это валидный HQL, но не наоборот: HQL поддерживает больше возможностей (например, `insert ... select`, которого нет в JPQL).

Главное отличие от SQL — вы оперируете не таблицами и колонками, а сущностями и их полями. В HQL `Book` — это Java-класс, а `book.title` — его поле. Прямое обращение к именам таблиц и колонок БД запрещено. За счёт этого HQL компактнее SQL и переносим между БД.

Пример сопоставления:
```sql
-- SQL
select book.title, pub.name
from Book as book
join Publisher as pub on book.publisherId = pub.id
where book.title like 'Hibernate%'
order by book.title
```

```java
// HQL
select book.title, pub.name
from Book as book
join book.publisher as pub
where book.title like 'Hibernate%'
order by book.title
```

Обратите внимание: join идёт по ассоциации (`book.publisher`), а не по колонке с внешним ключом. Hibernate сам знает, как её развернуть.

**Ключевые возможности HQL, которые нужно знать:**

- Параметры: именованные (`:name`) и позиционные (`?1`). Именованные предпочтительнее для читаемости, позиционные — для native-запросов.
- `JOIN FETCH` — главный инструмент борьбы с N+1. Загружает ассоциацию сразу, одним запросом.
- DTO-проекции: можно сразу вернуть не сущность, а `new com.example.dto.BookDto(book.title, pub.name)`. Это экономит память и не создаёт managed-объекты.
- `update` / `delete` — массовые операции (bulk update/delete), которые выполняются одним SQL и обходят Persistence Context (сущности в памяти не обновятся — это подводный камень).

**Подводные камни HQL:**

- Bulk update/delete не синхронизируются с кэшем 1-го уровня. Если вы загрузили `Book` в сессию, а потом сделали `update Book set title = ...`, объект в памяти останется со старым title. Нужен `session.clear()` или `refresh()`.

- `JOIN FETCH` двух коллекций одновременно даёт `MultipleBagFetchException` или декартово произведение. Решение — `@BatchSize` / `SUBSELECT`, либо разбивка на два запроса.

- `JOIN FETCH` + пагинация (`setMaxResults`) может дать неверный результат: Hibernate применяет limit в памяти, а не в SQL. Это известное ограничение.

### Criteria API: запросы как код

Criteria API — это программный способ построения запроса. Вместо строки вы собираете запрос из объектов: `CriteriaBuilder`, `CriteriaQuery`, `Root`, `Predicate`. Это даёт типобезопасность (компилятор проверяет имена полей, если используете метамодель) и гибкость для динамических условий.

Когда Criteria API незаменим:
- Экраны поиска с переменным набором фильтров. Например, пользователь может задать цену, категорию, бренд — или ничего. Собирать HQL-строку с `if` — источник багов; Criteria API делает это чисто.
- Динамическая сортировка и пагинация с проверкой типов.
- Построение запросов в библиотеках и фреймворках, где вы не знаете заранее структуру сущностей.

Пример (упрощённо):
```java
CriteriaBuilder cb = session.getCriteriaBuilder();
CriteriaQuery<Book> cq = cb.createQuery(Book.class);
Root<Book> book = cq.from(Book.class);

List<Predicate> predicates = new ArrayList<>();
if (title != null) predicates.add(cb.like(book.get("title"), "%" + title + "%"));
if (minPrice != null) predicates.add(cb.ge(book.get("price"), minPrice));

cq.where(predicates.toArray(new Predicate[0]));
cq.orderBy(cb.asc(book.get("title")));

List<Book> result = session.createQuery(cq).getResultList();
```

Минусы Criteria API:
- Многословность. Простой запрос превращается в 10–15 строк.
- Читаемость хуже, чем у HQL. Особенно для сложных join’ов.
- Не для «одноразовых» запросов. Если запрос статический — HQL короче и понятнее.

Практическое правило: статические запросы — HQL/JPQL; динамические (поиск, фильтры) — Criteria API.

### Native SQL: когда ORM бессилен

Иногда нужно спуститься на уровень БД. Native SQL оправдан, когда:
- Нужна специфичная для БД фича (оконные функции, `LATERAL JOIN`, `hints`, `FOR UPDATE SKIP LOCKED`, специфичный синтаксис).
- Запрос слишком сложен для HQL и проще написать на SQL, чем собирать через Criteria.
- Нужна максимальная производительность в узком месте, где HQL генерирует неоптимальный SQL.
- Работа со stored procedures.

Пример:
```java
Book book = session.createNativeQuery(
    "select * from Books where isbn = ?1", Book.class)
    .setParameter(1, isbn)
    .getSingleResult();
```

Главный подводный камень native-запросов: Hibernate по умолчанию не делает flush перед их выполнением, потому что не знает, какие таблицы затронет запрос. Если в Persistence Context есть несохранённые изменения — native-запрос может вернуть устаревшие данные. Решение — явный `session.flush()` перед запросом или настройка `FlushMode`.

Второй камень — маппинг результата. Для простых случаев (`select *`, совпадающий с сущностью) Hibernate выведет маппинг сам. Для сложных запросов (алиасы, агрегаты, join’ы) нужен `@SqlResultSetMapping` или ручной разбор `Object[]` — это громоздко и хрупко.

Третий камень — переносимость. Native SQL привязывает вас к диалекту БД. Если планируете смену БД — используйте его точечно.

### Spring Data JPA: как это выглядит

В Spring Boot вы редко пишете `session.createQuery()` напрямую. Вместо этого — репозитории Spring Data JPA, которые предлагают три уровня абстракции:

1. Derived queries (из имени метода). `findByEmailAddressAndLastname(String email, String lastname)` автоматически превращается в JPQL: `select u from User u where u.emailAddress = ?1 and u.lastname = ?2`. Работает для простых запросов, но имена становятся громоздкими при 3+ условиях.

2. `@Query` с JPQL/HQL. Явный запрос на методе репозитория. Это стандарт для запросов средней сложности:
```java
@Query("select b from Book b join fetch b.author where b.title like %:title%")
List<Book> findWithAuthorByTitle(@Param("title") String title);
```

3. `@Query(nativeQuery = true)`. Native SQL, когда JPQL не хватает. Флаг `nativeQuery` явно говорит Spring Data, что это не JPQL.

> Важно: Spring Data JPA не генерирует JPQL для `UPDATE` и `DELETE` из имени метода — только для `SELECT`. Для модификаций нужен `@Query` + `@Modifying`

### Что когда использовать

| Подход | Когда выбирать | Плюсы | Минусы
|--|--|--|--
| HQL/JPQL | Статические запросы, 80% случаев | Компактно, переносимо, читаемо | Не для динамики; строки не проверяются компилятором
| Criteria API | Динамические фильтры, поиск, библиотеки | Типобезопасно, гибко | Многословно, хуже читается
| Native SQL | Специфика БД, сложные запросы, производительность | Полный контроль над SQL | Непереносимо, нужен ручной маппинг, flush-нюансы
| Spring Data (derived) | Простые CRUD и выборки | Минимум кода | Громоздкие имена, только SELECT
| Spring Data `@Query` | Запросы средней сложности | Явно, читаемо, в репозитории | Строки не проверяются компилятором

### Что нужно запомнить

- HQL — надмножество JPQL. Пишите на JPQL для переносимости; используйте HQL-фичи осознанно.
- HQL оперирует сущностями, а не таблицами. Это его сила (компактность, переносимость) и ограничение (нельзя использовать специфику БД).
- Criteria API — для динамики, HQL — для статики. Не пытайтесь строить простой запрос через Criteria — это оверкилл.
- Native SQL — точечный инструмент. Всегда помните про `flush` и маппинг результата.
- `JOIN FETCH` — ваш главный друг против N+1, но с ним есть ограничения (пагинация, две коллекции).
- Bulk update/delete в HQL не синхронизируются с кэшем 1-го уровня. После них нужен `clear()`.
- В Spring Data 90% запросов — это `@Query` с JPQL. Derived queries — для простого, native — для исключений.


## Кэширование (Caching)

Кэширование в Hibernate — это многоуровневая система, и понимание её архитектуры критично для производительности. Главное правило: кэширование выключено по умолчанию (кроме кэша первого уровня), и включать его нужно осознанно, для конкретных данных. Система состоит из трёх независимых слоёв, каждый со своей зоной ответственности.

### Кэш первого уровня (First-Level Cache)

Это фундамент, который нельзя отключить. Он всегда активен и привязан к конкретной сессии (`Session`/`EntityManager`).

- Что это: По сути, это и есть Persistence Context. Все сущности, загруженные в рамках одной сессии, попадают в этот кэш.

- Область видимости: Только в пределах одной сессии (обычно одной транзакции). После закрытия сессии кэш уничтожается.

- Гарантии: Обеспечивает identity map (повторный `get` по тому же id вернёт тот же Java-объект) и dirty checking (Hibernate сравнивает текущее состояние с snapshot при `flush`).

- Управление: Вы не можете его отключить, но можете управлять содержимым: `session.evict(entity)` удаляет конкретный объект, `session.clear()` полностью очищает кэш. Это полезно при пакетной обработке больших объёмов данных, чтобы избежать переполнения памяти.

### Кэш второго уровня (Second-Level Cache)

Это общий кэш, который живёт на уровне `SessionFactory` и разделяется между всеми сессиями. Он предназначен для данных, которые редко меняются и часто читаются.

- Область видимости: Уровень процесса (или кластера, если используется распределённый провайдер). Данные переживают закрытие сессии.
- Что кэшируется: Состояние сущностей (по их id). Не кэширует результаты запросов.
- По умолчанию выключен. Чтобы включить, нужно выполнить три условия:
    1. Активировать кэш в настройках (`hibernate.cache.use_second_level_cache=true`).
    2. Подключить провайдер (EhCache, Caffeine, Infinispan, Redis и т.д.).
    3. Явно пометить каждую сущность аннотацией `@Cache`. Глобальное включение не кэширует всё подряд — сущности должны «подписаться» на кэширование.

Стратегии конкурентного доступа (`CacheConcurrencyStrategy`):
При настройке `@Cache` вы обязаны указать стратегию, которая определяет, как кэш ведёт себя при конкурентных обновлениях.

| Стратегия | Когда использовать | Особенности
|--|--|--
| `READ_ONLY` | Неизменяемые справочные данные | Самая быстрая и безопасная. При попытке обновления — исключение.
| `NONSTRICT_READ_WRITE` | Обновления редки и маловероятны | Без блокировок. Есть небольшой риск прочитать устаревшие данные во время обновления.
| `READ_WRITE` | Обновления возможны | Использует «мягкие» блокировки для предотвращения чтения устаревших данных во время транзакции.
| `TRANSACTIONAL` | Строгая согласованность | Полноценные транзакционные блокировки. Требует поддержки от провайдера кэша.

Управление: `sessionFactory.evict(Entity.class, id)` позволяет точечно удалить сущность из кэша второго уровня.

### Кэш запросов (Query Cache)

Это специализированный кэш для результатов запросов. Он работает как дополнение ко второму уровню и не заменяет его.

- Что кэшируется: Результат выполнения запроса (JPQL/Criteria) с конкретным набором параметров. Кэшируются только идентификаторы найденных сущностей и значения скалярных полей, но не состояние самих сущностей.
- Зависимость: Поскольку кэш запросов хранит только id, для получения самих данных Hibernate обратится в кэш второго уровня. Если сущности там нет, будет выполнен запрос к БД. Поэтому кэш запросов всегда используется в паре с кэшем второго уровня.
- Как включить:
    1. Активировать глобально: `hibernate.cache.use_query_cache=true`.
    2. Для каждого конкретного запроса вызвать `.setCacheable(true)`.
- Инвалидация: Кэш запросов очень чувствителен к изменениям. При любом обновлении таблицы, участвующей в запросе, соответствующие закэшированные результаты становятся недействительными. Hibernate отслеживает это через регион `UpdateTimestampsCache`.

### Подводные камни и типичные ошибки

1. Ожидание, что кэш второго уровня заработает «сам». Самая частая ошибка. Включение глобальной настройки бесполезно, если на сущностях нет `@Cache`.
2. Кэширование «волатильных» данных. Если сущность часто обновляется, кэш будет постоянно инвалидироваться, создавая накладные расходы и не принося пользы. Кэшируйте только «справочные» или редко меняющиеся данные.
3. Проблемы согласованности в кластере. При использовании нескольких инстансов приложения обычный кэш второго уровня (например, на основе локальной памяти) не синхронизируется между ними. Один инстанс может обновить данные, а другой — продолжать отдавать устаревшие из своего кэша. Решение — распределённый кэш (Redis, Infinispan, Hazelcast), который синхронизирует инвалидацию между узлами.
4. Использование `READ_WRITE` без поддержки блокировок. Стратегия `READ_WRITE` требует, чтобы провайдер кэша поддерживал блокировки. Не все провайдеры это умеют, и в документации есть предупреждения на этот счёт.
5. Слишком большой кэш запросов. Кэш запросов имеет смысл только для часто повторяющихся запросов с одинаковыми параметрами. Для остальных запросов он создаёт лишний overhead на инвалидацию.

### Итог

1. Кэш 1-го уровня — всегда включён, живёт в рамках сессии, обеспечивает identity и dirty checking. Управляйте им через `evict`/`clear` при массовой обработке.
2. Кэш 2-го уровня — общий для всех сессий, но выключен по умолчанию. Требует провайдера и явной пометки `@Cache` на каждой сущности. Выбирайте стратегию (`READ_ONLY`, `READ_WRITE` и т.д.) исходя из частоты обновлений данных.
3. Кэш запросов — кэширует только id результатов для повторяющихся запросов. Всегда работает в связке с кэшем второго уровня, иначе смысла в нём нет.
4. Кэширование — это компромисс между скоростью чтения и риском получить устаревшие данные. Не кэшируйте всё подряд; начинайте с `READ_ONLY` для справочников.
5. В кластере используйте распределённый кэш (Redis/Infinispan), иначе согласованность данных будет нарушена.

## Управление транзакциями и блокировки (Transactions & Locking)

Hibernate и Spring обеспечивают целостность данных при параллельной работе. Здесь важно разобраться в двух ключевых механизмах: транзакциях, которые определяют границы единицы работы, и блокировках, которые разрешают конфликты при одновременном доступе.

### Управление транзакциями в Spring и Hibernate

В основе лежит аннотация `@Transactional`, которая через Spring AOP (прокси) оборачивает метод в транзакцию и решает, когда её закоммитить или откатить.

**Ключевой момент — правила отката (Rollback Rules):**
По умолчанию Spring откатывает транзакцию только для непроверяемых исключений (`RuntimeException` и `Error`). Для проверяемых (`checked`, наследники `Exception`, но не `RuntimeException`) транзакция по умолчанию коммитится. Это частое место для ошибок: разработчик бросает `IOException` и ожидает отката, а данные частично сохраняются.

```java
// Явное управление откатом
@Transactional(
    rollbackFor = { IOException.class, PaymentGatewayException.class }, // откат для checked
    noRollbackFor = { OptimisticLockException.class } // коммит для RuntimeException (например, чтобы потом повторить)
)
public void processOrder(Order order) throws IOException {
    // ...
}
```

> Важно: Откат сработает, только если исключение "вылетит" за пределы `@Transactional`-метода. Если вы поймали его внутри, Spring о нём не узнает и транзакция закоммитится

**Уровни изоляции (Isolation):**
Spring даёт возможность явно указать уровень изоляции (`Isolation.READ_COMMITTED`, `REPEATABLE_READ` и т.д.). По умолчанию используется `Isolation.DEFAULT`, который полагается на настройки базы данных. Это может быть опасно, если разные среды (например, staging и production) используют разные БД с разными уровнями по умолчанию — поведение кода станет непредсказуемым.

**Распространение (Propagation):**
Определяет, как транзакция метода соотносится с уже существующей. Например, `Propagation.REQUIRES_NEW` всегда создаёт новую транзакцию, приостанавливая внешнюю, что полезно для операций, которые должны быть закоммичены независимо (например, аудит).

### Блокировки (Locking): стратегии разрешения конфликтов

Hibernate, как и JPA, предлагает два принципиально разных подхода к блокировкам: оптимистичный и пессимистичный.

**Оптимистичная блокировка (Optimistic Locking)**
Основана на предположении, что конфликты случаются редко. Транзакции не блокируют данные при чтении, но перед коммитом проверяют, не изменил ли кто-то данные с момента их чтения.

Реализуется через поле с аннотацией `@Version` (число или `Timestamp`). При каждом обновлении Hibernate выполняет SQL вида `UPDATE ... SET version = version + 1 WHERE id = ? AND version = ?`. Если строк, удовлетворяющих условию `WHERE`, нет (версия изменилась), выбрасывается `OptimisticLockException`.

Когда использовать: Для большинства веб-приложений и сценариев с редкими конфликтами. Это масштабируемый и производительный подход.

Режимы `LockModeType`: `OPTIMISTIC` (проверка при коммите) и `OPTIMISTIC_FORCE_INCREMENT` (принудительное увеличение версии даже без изменений).

**Пессимистичная блокировка (Pessimistic Locking)**
Основана на предположении, что конфликты будут. Данные блокируются в базе данных на время транзакции, не позволяя другим транзакциям изменять или читать их.

Реализуется через `LockModeType` (например, `PESSIMISTIC_WRITE`), что транслируется в SQL `SELECT ... FOR UPDATE`.

Когда использовать: Для критических операций с высокой конкуренцией (например, списание денег со счёта), где откат и повторная попытка нежелательны или слишком дороги.

Риски: Блокировки удерживаются до конца транзакции, что может привести к взаимоблокировкам (deadlocks) и снижению пропускной способности.

### Типичные ошибки и подводные камни

1. Неверное понимание правил отката: Ожидание отката для проверяемого исключения или, наоборот, коммит после `RuntimeException`, который был пойман внутри метода.
2. "Отравленная" сессия: После исключения (например, `DataIntegrityViolationException`) сессия Hibernate может быть помечена как `rollback-only`. Дальнейшие операции в этой транзакции будут падать. Решение — использовать `Propagation.REQUIRES_NEW` для изоляции сбойной операции.
3. `OptimisticLockException` "на ровном месте": Может возникать при использовании `orphanRemoval` и сложных графов объектов, когда Hibernate пытается обновить уже удалённую сущность. Иногда помогает `em.flush()` и `em.clear()` для синхронизации состояния.
4. Смешивание стратегий: Наличие `@Version` (оптимистичная блокировка) не отменяет проверку версии даже при использовании `SELECT ... FOR UPDATE` (пессимистичной блокировки). Если другая транзакция изменила данные, `OptimisticLockException` всё равно будет выброшено при обновлении.
5. Долгие транзакции: Удержание пессимистичной блокировки или открытой сессии на время взаимодействия с пользователем (например, через `OpenSessionInView`) — прямой путь к исчерпанию пула соединений и deadlock'ам.

### Что и когда использовать

| | Оптимистичная | Пессимистичная
|--|--|--
| Принцип | Конфликты редки. Проверка перед коммитом. | Конфликты вероятны. Блокировка в БД.
| Реализация | `@Version` | `LockModeType.PESSIMISTIC_WRITE` (`SELECT FOR UPDATE`)
| Когда использовать | Большинство веб-приложений, CRUD, редкие обновления. | Критические операции с высокой конкуренцией (финансы, резервирование).
| Риски | `OptimisticLockException` при конфликте (требует обработки/повтора). | Deadlocks, снижение пропускной способности, долгие блокировки.

### Итоги

1. Spring по умолчанию откатывает только `RuntimeException` и `Error`. Для проверяемых исключений откат нужно указывать явно через `rollbackFor`.
2. Исключение должно "вылететь" из `@Transactional`-метода, чтобы Spring выполнил откат. Не глотайте исключения внутри.
3. Оптимистичная блокировка (`@Version`) — это проверка версии при обновлении. Она не блокирует данные, а лишь сообщает о конфликте (`OptimisticLockException`). Это выбор по умолчанию для большинства систем.
4. Пессимистичная блокировка (`SELECT FOR UPDATE`) — это реальная блокировка на уровне БД. Используйте её точечно, только там, где без неё возникнет критическая ошибка.
5. `Isolation.DEFAULT` может привести к разному поведению в разных средах. Для важных операций указывайте уровень изоляции явно.
6. `Propagation.REQUIRES_NEW` — ваш инструмент для изоляции сбойных операций (например, логирования), которые не должны влиять на основную транзакцию.


## Производительность и типичные проблемы

Проблемы с производительностью редко бывают виной самого Hibernate; чаще всего они вызваны его неправильным использованием. Ключ к успеху — найти эти проблемы до того, как они проявятся в продакшене.

### Как найти проблемы до продакшена

Проблемы с производительностью почти не видны на маленькой тестовой базе с одним пользователем, но катастрофически проявляются на реальных данных и под нагрузкой. Поэтому начинать нужно с настройки диагностики.

1. Логирование SQL и статистики Hibernate
Включите логирование SQL-запросов и статистики, чтобы видеть, что именно Hibernate отправляет в базу данных.
```properties
# Показывать SQL в логах (в dev-окружении)
spring.jpa.show-sql=true
spring.jpa.properties.hibernate.format_sql=true

# Собирать подробную статистику (количество запросов, время выполнения)
hibernate.generate_statistics=true
logging.level.org.hibernate.stat=DEBUG
```

Статистика покажет общее количество запросов, время их выполнения и самую важную метрику — количество JDBC-вызовов на одну сессию.

2. Логирование медленных запросов
Начиная с Hibernate 5.4.5, можно указать порог, и Hibernate будет логировать только те запросы, которые выполняются дольше него.
```properties
# Логировать запросы, выполняющиеся дольше 100 мс
hibernate.session.events.log.LOG_QUERIES_SLOWER_THAN_MS=100
```

Это помогает быстро находить «тяжелые» места.

### Проблема №1: N+1 (и как её лечить)

Это самая распространенная причина проблем с производительностью в Java-приложениях с ORM. Мы уже разбирали её механизм: вместо одного запроса Hibernate выполняет `1 + N` запросов.

Вот основные стратегии лечения, от самых предпочтительных до вспомогательных.

**Стратегия 1: `JOIN FETCH` (или `@EntityGraph`)**

Это самый прямой и эффективный способ, когда вы заранее знаете, что данные понадобятся. Вы явно указываете Hibernate загрузить ассоциацию в том же SQL-запросе через `JOIN`.

```java
// В JPQL-запросе
@Query("SELECT o FROM Order o JOIN FETCH o.customer WHERE o.status = :status")
List<Order> findWithCustomerByStatus(@Param("status") Status status);
```

`@EntityGraph` делает то же самое, но декларативно на уровне Spring Data репозитория:

```java
@EntityGraph(attributePaths = {"customer", "items"})
List<Order> findByStatus(Status status);
```

*Плюсы:* Один запрос к БД, максимальная производительность для известных сценариев.

*Минусы:* Работает чисто только для одной ассоциации-коллекции за запрос. При попытке сделать `JOIN FETCH` для двух `List`-коллекций одновременно вы получите `MultipleBagFetchException` или декартово произведение.

**Стратегия 2: Пакетная загрузка (`@BatchSize` / `default_batch_fetch_size`)**

Это «предохранитель» и отличный вариант, когда вы не можете (или не хотите) менять все запросы. Hibernate продолжает использовать ленивую загрузку, но когда вы обращаетесь к первой сущности в «пачке», он собирает ID всех остальных и загружает их одним запросом с `IN (...)`.

```properties
# Глобальная настройка: Hibernate будет группировать ленивые загрузки в пачки по 50
spring.jpa.properties.hibernate.default_batch_fetch_size=50
```

Или точечно на коллекции: `@BatchSize(size = 25)`.

*Плюсы:* Не требует изменения запросов, легко включается глобально, отлично работает как «страховка» от случайных N+1.

*Минусы:* Не убирает N+1 полностью, а сокращает количество запросов с `N` до `N / batchSize`. Остается несколько round-trip’ов к БД.

**Стратегия 3: DTO-проекции**

Если для чтения нужны не все поля сущности, а только несколько, не загружайте сущность целиком. Сделайте запрос, который сразу возвращает DTO (например, `record`).
```java
@Query("SELECT new com.example.dto.OrderSummary(o.id, o.status, c.name) " +
       "FROM Order o JOIN o.customer c WHERE o.status = :status")
List<OrderSummary> findSummariesByStatus(@Param("status") Status status);
```

*Плюсы:* Самый быстрый и безопасный способ для read-only эндпоинтов. Вы загружаете ровно столько данных, сколько нужно, не создаете managed-сущности и полностью исключаете N+1 и dirty checking.

*Минусы:* Подходит только для чтения; для операций изменения нужны сущности.

*Иерархия выбора:* В идеале для каждого сценария доступа выбирать стратегию осознанно. На практике часто используется комбинация: `JOIN FETCH` для известных «горячих» путей и `default_batch_fetch_size` как глобальная страховка.

### Проблема №2: Антипаттерн `Open Session in View` (OSIV)

Spring Boot по умолчанию включает `spring.jpa.open-in-view=true`. Это значит, что Hibernate-сессия остается открытой на весь HTTP-запрос, включая рендеринг ответа или JSON-сериализацию`.

Чем это опасно:
- Скрывает N+1. Когда Jackson сериализует объект и дергает ленивую коллекцию, Hibernate молча выполняет запрос. Вы даже не подозреваете об этом, пока не посмотрите в логи.
- Непредсказуемые запросы. Запросы к БД могут выполняться на этапе сериализации, уже после закрытия транзакции.
- Долгие соединения. Хотя OSIV не держит соединение открытым всё время, он позволяет выполнять запросы в любой момент жизненного цикла запроса, что может привести к непредсказуемому использованию пула соединений.

Решение: Всегда отключайте OSIV в продакшене.

```properties
spring.jpa.open-in-view=false
```

После отключения любые проблемы с ленивой загрузкой станут явными (`LazyInitializationException`), и вы будете вынуждены решать их правильно — через `JOIN FETCH`, `@EntityGraph` или DTO, а не прятать под ковер.

### Проблема №3: Медленный батчинг (массовые вставки/обновления)

Если вы сохраняете 1000 сущностей через `saveAll()`, Hibernate по умолчанию выполнит 1000 отдельных `INSERT`, что может занять минуты. Батчинг позволяет объединить их в несколько пакетов.

Конфигурация для включения батчинга:
```properties
spring.jpa.properties.hibernate.jdbc.batch_size=50
spring.jpa.properties.hibernate.order_inserts=true
spring.jpa.properties.hibernate.order_updates=true
spring.jpa.properties.hibernate.jdbc.batch_versioned_data=true
```

`batch_size`: количество операторов в одном пакете (оптимально 20–50).

`order_inserts` / `order_updates`: группируют однотипные операции, что необходимо для эффективного батчинга.

**Критический подводный камень:** `GenerationType.IDENTITY`
Если ваша сущность использует `@GeneratedValue(strategy = GenerationType.IDENTITY)`, батчинг работать не будет. Hibernate вынужден выполнять каждый `INSERT` отдельно, чтобы немедленно получить сгенерированный базой ID. Используйте `GenerationType.SEQUENCE`. Hibernate может заранее выделить блок ID из последовательности и затем выполнить все вставки одним пакетом.

### Проблема → решение
| Проблема | Симптом | Лучшее решение | Альтернатива / Страховка
|--|--|--|--
| N+1 | Много однотипных `SELECT` с разными параметрами | `JOIN FETCH` / `@EntityGraph` (для известных сценариев) | `@BatchSize` / `default_batch_fetch_size` (глобально); DTO-проекции (для read-only)
| `LazyInitializationException` | Ошибка при доступе к ленивому полю вне транзакции | Загружать данные явно внутри транзакции (`JOIN FETCH`) | Отключить `open-in-view` и использовать DTO
| `MultipleBagFetchException` | Ошибка при `JOIN FETCH` двух `List`-коллекций | Загружать коллекции отдельными запросами | Использовать `Set` вместо `List` (не всегда помогает); `@BatchSize`
| Медленный `saveAll` | Вставка/обновление тысяч записей занимает минуты | `hibernate.jdbc.batch_size` + `GenerationType.SEQUENCE` | Периодический `flush()` + `clear()` для больших объемов
| Скрытые запросы | Приложение «тормозит» без видимых причин | Отключить `spring.jpa.open-in-view` | Включить логирование SQL и статистику Hibernate

### Итог

1. Проблемы с производительностью Hibernate — это почти всегда следствие его неправильного использования, а не его внутренних дефектов.
2. Диагностика — прежде всего. Включите `show-sql` и `generate_statistics` в dev-окружении, чтобы видеть реальное количество и время запросов.
3. N+1 — враг №1. Лечите его `JOIN FETCH` (для известных сценариев) или `@BatchSize` (как глобальную страховку). Для read-only эндпоинтов DTO-проекции — самое чистое и быстрое решение.
4. `open-in-view` — антипаттерн для REST API. Отключите его (`spring.jpa.open-in-view=false`). Это сделает проблемы с ленивой загрузкой явными и заставит вас решать их правильно.
5. Батчинг не работает с `IDENTITY`. Для эффективных массовых вставок используйте `GenerationType.SEQUENCE`.
6. Осознанно выбирайте стратегию загрузки для каждого сценария. `LAZY` — правильный default, но он требует явного управления через `JOIN FETCH`, `@EntityGraph` или DTO, особенно при отключенном OSIV.
