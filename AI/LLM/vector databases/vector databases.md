# Автосалон векторных баз. 

## 🚙 pgvector — универсал, который уже стоит в гараже

Это не отдельная база. Это расширение Postgres: одна команда — и векторы живут рядом с вашими обычными данными.

Под капотом: тип `vector`, два индекса (HNSW и IVFFlat), три основных расстояния (L2, косинус, скалярное произведение). С версии 0.6 — halfvec (вдвое легче) и sparse-векторы. С 0.7 — итеративные сканы индекса для поиска с фильтрами.

### Что едет отлично:
- **Транзакции ACID**: эмбеддинг и его метаданные записываются атомарно. Никакой синхронизации двух хранилищ
- **Джойны**: «найди похожие документы И подтяни связанные строки» — без выгрузки в приложение
- **Бэкапы, мониторинг, права, реплики** — всё, что вы уже настроили для Postgres, работает и для векторов
- **Row Level Security** — мультитенантность из коробки

### Где застрянет:
- **Вертикальный потолок**. Комфортно — до ~1 млн векторов, до ~10 млн — с тюнингом (halfvec, партиции, pgvectorscale от Timescale). Дальше — другая лига
- **Аппетит к памяти**: миллион векторов × 1536 измерений ≈ 6 ГБ сырых данных — и примерно столько же добавит индекс HNSW (pgvector хранит копию каждого вектора внутри графа). Закладывайте 12–16 ГБ RAM/кэша, а не 6
- **Перестройка индекса на больших объёмах** — часы, не минуты

### Что сломается, если ездить не по инструкции:
- **Фильтры + ANN**: у вас три инструмента, выбирайте по сценарию. Голый WHERE применяется после того, как HNSW вернул свой топ-k — строк может оказаться меньше, чем просил LIMIT:
    - **Pre-filtering через b-tree** — классика RAG. Индекс по колонке фильтра (`CREATE INDEX ON documents ((meta->>'year'))`); на селективном фильтре Postgres сначала отберёт строки, а расстояния честно посчитает по ним. Recall 100%, и планнер обычно сам выбирает этот путь
    - **Iterative scans (v0.7+)** — `SET hnsw.iterative_scan = strict_order`: индекс продолжает обход графа, пока фильтр не наберёт достаточно строк. Выбор, когда фильтр матчит много строк и b-tree перебирал бы полтаблицы
    - **Overfetch** — берём LIMIT × 5–10 и фильтруем в приложении. Быстро, грязно, для прототипа сойдёт
- **Лимиты размерностей**. Хранить можно до 16 000 измерений, а индексировать: `vector` — до 2 000, `halfvec` — до 4 000. Модель на 3072 (text-embedding-3-large)? В `vector` не индексируется — в `halfvec` влезает (fp16, потери минимальны). Дальше 4 000: усечение под Matryoshka-модель (почти без потерь) или переезд в специализированную БД — Qdrant и Milvus индексируют значительно больше
- **Recall не радует** — поднимите `hnsw.ef_search` (дефолт всего 40)
- **Частые UPDATE векторов → bloat**: каждая правка переписывает ~6 КБ строки. Массовая перегенерация эмбеддингов — отдельная операция, и с VACUUM после

**Цена владения**: ПО бесплатное, лицензия Postgres — максимально пермиссивная. Доплат ноль, пока вашего инстанса хватает по CPU/RAM. Есть у RDS, Aurora, Cloud SQL, AlloyDB, Azure, Supabase, Neon.

**Механики и запчасти**: найти водителя легко — любой бэкендер уже сидел за рулём. Интеграции с ORM везде (Django, Rails, SQLAlchemy, Prisma). Честный нюанс: исторически проект тянет один очень продуктивный человек (Эндрю Кейн), комьюнити растёт, а вокруг — экосистема компаний (Supabase, Neon, Timescale), строящих на pgvector бизнес. Контраргумент: это расширение Postgres, а не чёрный ящик — в худшем случае у вас остаётся документированный SQL-тип и понятные алгоритмы.

`✅` Берите, если: Postgres уже есть, векторов меньше ~миллиона, нужна консистентность (RAG поверх своей базы)

`❌` Проезжайте мимо, если: миллиарды векторов или распределённый масштаб — универсал не превращается в поезд

Тест-драйв:
```sql
CREATE EXTENSION vector;

CREATE TABLE documents (
  id bigserial PRIMARY KEY,
  content text,
  meta jsonb,
  embedding vector(1536)
);

CREATE INDEX ON documents
USING hnsw (embedding vector_cosine_ops);

-- b-tree по колонке фильтра → точный pre-filtered поиск
CREATE INDEX ON documents ((meta->>'year'));

-- операторы: <=> косинус | <-> L2 | <#> отрицательное скалярное произведение
-- сортировка по возрастанию: меньшее значение = ближе
SELECT id, content FROM documents
WHERE meta->>'year' = '2024'
ORDER BY embedding <=> $1
LIMIT 10;
```

Нюанс для привыкших к NumPy/FAISS: `<#>` возвращает отрицательное скалярное произведение — pgvector делает так, что все операторы сортируются по возрастанию.

Если вы знаете SQL — вы уже умеете pgvector. В этом вся машина.


## 🛴 Chroma — электросамокат, который заводится за 90 секунд

`pip install chromadb` — и вы уже едете. Ни сервера, ни портов, ни API-ключей.

**Под капотом**: open-source база эмбеддингов (Apache 2.0, Python-first, ядро на Rust с 0.4). 

**Embedded-режим**: используйте `PersistentClient`, чтобы данные легли в SQLite + Parquet на диск (а базовый `Client()` живёт в памяти и теряет данные при перезапуске — классическая неожиданность первого дня). Захотели поделиться с командой — одна команда превращает самокат в HTTP-сервер или контейнер.

### Что едет отлично:
- Три строки до первого поиска, эмбеддинги включены: локальная ONNX-модель по умолчанию — без OpenAI-ключа, без постоянной сети (модель скачивается один раз, ~80 МБ, при первом запуске), без счетов
- Стандарт всех RAG-туториалов: интеграции с LangChain и LlamaIndex первоклассные
- Фильтры по метаданным (`where`) и по содержимому документа (`where_document`)
- Косинус вместо дефолтного L2 — один параметр
- Ваши данные — и правда ваши: `collection.get()` выгружает всё. Lock-in измеряется часами, а не месяцами

### Где застрянет:
- **Одна нода by design — distributed-режима нет**. Единицы миллионов векторов — комфортно, десятки миллионов — экспедиция с костылями
- **HNSW живёт в RAM**: миллион × 1536 ≈ 6 ГБ сырых данных плюс столько же на граф
- **Durability прототипного уровня**: SQLite + периодические срезы Parquet. Падение процесса может стоить последних записей
- Нет BM25-гибрида, квантизации, RBAC — в прототипе этого не замечаешь, в проде — очень

### Что сломается, если ездить не по инструкции:
- **Самокат, который сам уехал в прод**. Классика: прототип растёт, «да уже готово, выкатываем» — и на 5 млн векторов вы ищете несуществующий кластер. Миграция в «настоящую» БД — день работы, но перепланировать архитектуру во время инцидента — день, которого у вас нет
- **Сигналки нет**: максимум токен-аутентификация, TLS — руками через реверс-прокси. «Он же только в офисной сети» — знаменитые последние слова
- Между мажорными версиями менялся формат хранения: changelog читаем до апгрейда

**Цена владения**: бесплатно, Apache 2.0. Chroma Cloud существует, но честный сценарий самоката — «инфраструктуры нет вообще»

**Механики и запчасти**: вакансий на «Chroma-инженера» не существует, потому что не нужны — любой Python-разработчик чинит самокат отвёрткой. Комьюнити одно из крупнейших среди векторных БД.

`✅` **Берите, если**: прототипируете RAG, изучаете эмбеддинги, гоняете оценки в CI, делаете личный тул, который не увидит интернет

`❌` **Проезжайте мимо, если**: база держит прод с платящими пользователями — арендуйте машину, а не самокат

**Тест-драйв за 90 секунд:**
```python
import chromadb
from chromadb.utils import embedding_functions

client = chromadb.PersistentClient(path="./chroma_data")

# явная локальная модель — надёжно и без warnings
default_ef = embedding_functions.DefaultEmbeddingFunction()

collection = client.get_or_create_collection(
    name="docs",
    embedding_function=default_ef,
    metadata={"hnsw:space": "cosine"}
)

collection.add(
    ids=["1", "2"],
    documents=["Quarterly report 2024", "Legal contract draft"],
    metadatas=[{"year": 2024}, {"year": 2024}],
)

# эмбеддинги локальные и автоматические — модель скачается один раз (~80 МБ)
res = collection.query(
    query_texts=["annual financial summary"],
    n_results=2,
    where={"year": 2024},
)
```

Если кажется слишком просто — так и задумано. Только помните: работа самоката в том, чтобы однажды уступить место настоящей машине.


## 🏎️ Qdrant — горячий хэтчбек

*Резкий разгон, точное рулевое — и багажник заметно больше, чем кажется снаружи.*

**Под капотом:** ядро на Rust, один бинарь или контейнер (для экспериментов есть даже embedded-режим в Python-клиенте). Apache 2.0. Фирменная фишка — filterable HNSW: граф строится с учётом payload-индексов, поэтому фильтр участвует в обходе графа, а не приклеивается сверху.

### Что едет отлично:
- Помните три инструмента фильтрации из выпуска про pgvector? Здесь фильтрация — часть самого индекса: «похожие, но только year=2024» — родная стихия этого автомобиля
- **Гибрид из коробки:** sparse-векторы с v1.7, Query API с prefetch и фьюжном (RRF/DBSF) с v1.10 - dense + sparse в одном запросе
- **Квантизация** — те самые «облегчённые сплавы»: int8 сжимает векторы ×4, binary ×32. Оригиналы могут лежать на диске, в RAM живут только сжатые копии. Сотни миллионов векторов на одной ноде — реальный сценарий, а не маркетинг
- **Multivectors (ColBERT-style):** несколько векторов на точку, late interaction. Такое из салона умеют единицы
- **Эксплуатация:** Prometheus-метрики, снапшоты, API-ключи + JWT RBAC

### Где застрянет:
- Эмбеддинги — сами. Это база, а не эмбеддер (контраст с самокатом прошлого выпуска). Клиенты на Python/JS/Go/Rust, интеграции с LangChain/LlamaIndex на месте
- **Distributed-режим** (шардирование, репликация, Raft) — настоящий ops: проще поезда, который приедет позже в этой серии, тяжелее Postgres
- **Бэкапы** — снапшоты руками. Никаких WAL и point-in-time recovery, как вы привыкли в Postgres
- **Тюнинг** — часть контракта: m, ef_construct, hnsw_ef, квантизация с rescore. Дефолты приличные, но хэтчбек любит, когда его настраивают

### Что сломается, если ездить не по инструкции:
- **Расстояние (COSINE/DOT/EUCLID/MANHATTAN) фиксируется при создании коллекции.** Ошиблись — полная переиндексация, «alter on the fly» нет
- **Payload-индексы:** забыли создать — фильтрованный поиск деградирует до сканов. Правильный порядок: коллекция → payload-индексы → загрузка. Индекс «постфактум» перестраивает HNSW-граф в фоне, чтобы проложить фильтруемые рёбра
- **Ловушка бенчмарков №1:** пока сегмент меньше `indexing_threshold` из optimizer-конфига, HNSW-граф для него не строится вовсе — поиск идёт полным перебором: быстро и с идеальным recall. Наивный бенчмарк на маленькой коллекции измеряет exact search, а не HNSW. Честные цифры — на объёмах, близких к боевым, либо явно понизьте `indexing_threshold`
- **Квантизация без rescoring режет recall.** Бинарная вообще чувствительна к модели: на одних эмбеддингах гениальна, на других провальна. Эталон для сравнения — поиск с exact=true. Тезис салона: бенчмарки вендоров — это реклама, проверяйте на своих данных
- **Named vectors**: создавали коллекцию с именованными векторами — в поиске передавайте имя через параметр using, иначе `400`

**Цена владения:** бесплатно, Apache 2.0. Есть Qdrant Cloud (managed и hybrid). Аппетит к RAM гибкий: квантизация + оригиналы на диске вместо «6 ГБ на миллион»

**Механики и запчасти:** за спиной Qdrant GmbH (Берлин), доки — одни из лучших в индустрии. «Инженеров Qdrant» на рынке мало, но это база, на которой бэкендер едет сам, а не зоопарк из двадцати подов

`✅` Берите, если: миллионы — сотни миллионов векторов, RAG с тяжёлыми фильтрами, self-host, нужна скорость без строительства железной дороги

`❌` Проезжайте мимо, если: вся логика живёт в SQL и нужны джойны (универсал делает это лучше), либо счёт на миллиарды и GPU — ждём поезд

### Тест-драйв:
```python
from qdrant_client import QdrantClient, models

# qdrant-client >= 1.10; для локальных опытов: QdrantClient(path="./qdrant_data")
client = QdrantClient(url="http://localhost:6333")

client.create_collection(
    collection_name="docs",
    vectors_config=models.VectorParams(size=1536, distance=models.Distance.COSINE),
)

# payload-индекс ДО загрузки — так строится filterable HNSW
client.create_payload_index(
    collection_name="docs",
    field_name="year",
    field_schema=models.PayloadSchemaType.INTEGER,
)

# embed() — ваша функция эмбеддингов (OpenAI, BGE, любая)
client.upsert(
    collection_name="docs",
    points=[
        models.PointStruct(id=1, vector=embed("Quarterly report 2024"), payload={"year": 2024}),
        models.PointStruct(id=2, vector=embed("Legal contract draft"), payload={"year": 2024}),
    ],
)

# фильтр участвует в обходе графа, а не приклеен сверху
# query_points возвращает QueryResponse — сами точки лежат в .points
res = client.query_points(
    collection_name="docs",
    query=embed("annual financial summary"),
    query_filter=models.Filter(
        must=[models.FieldCondition(key="year", match=models.MatchValue(value=2024))]
    ),
    limit=10,
).points

for point in res:
    print(point.id, point.score, point.payload)
```

Хэтчбек не притворяется универсалом и не строит рельсы — он просто быстро возит. А когда данные дорастут до прицепа, API не меняется: переезд в кластер идёт через снапшоты, приложение этого не замечает.


## 🚐 Weaviate — кроссовер в полной комплектации

Все опции уже с завода: векторизация, гибрид, мультитенантность. Вопрос один — кто будет их обслуживать.

**Под капотом:** ядро на Go, лицензия BSD-3-Clause, один контейнер на старт. Протокола три: REST, GraphQL и gRPC — по последнему v4-клиент ездит быстрее всего. Философия — «принесите данные, остальное сделает завод»: модули векторизации, гибрид, генерация включаются конфигом, а не внешним кодом.

### Что едет отлично:
- **Векторизация с завода:** подключаете модуль (локальные трансформеры, OpenAI, Cohere, мультимодальный CLIP) — и база эмбеддирует сама при вставке. Контраст с самокатом: там эмбеддер зашит наглухо, здесь — заводские опции на выбор
- **Гибрид по-заводски:** BM25F (лексический индекс уже внутри) + векторы в одном запросе, ручка alpha балансирует «семантика vs ключевые слова». Отдельный sparse-эмбеддер не нужен — в отличие от хэтчбека
- **Мультитенантность — фирменная фишка:** тенант = отдельный шард, изоляция поиска и производительности, активные/неактивные тенанты с холодным хранением. Для SaaS — то, что в других базах собирают руками из payload-фильтров
- **Generative search:** RAG внутри базы — генеративный модуль достраивает ответ рядом с найденными объектами
- **Cross-references:** объекты ссылаются друг на друга — мини-граф внутри векторной базы (без амбиций Neo4j)
- **Эксплуатация выше среднего:** штатные бэкапы в S3/GCS/Azure/на диск, Prometheus-метрики, OIDC-аутентификация. Хэтчбек со снапшотами руками позавидует

### Где застрянет:
- **Заводские опции требуют сервисной зоны:** self-host модули векторизации — это отдельные контейнеры, каждый ест RAM и требует присмотра. API-модули — зависимость от внешнего провайдера внутри вашей базы
- **Транзакций «как в Postgres» нет:** батчи — не ACID-операции
- **Изменение схемы:** что-то применяется на ходу, но смена векторизатора или типа свойства = переимпорт. Проектируйте схему до загрузки
- **Distributed-режим есть, но тюнинга хватает:** ef, efConstruction, квантизация (scalar/product/binary) с потерями recall

### Что сломается, если ездить не по инструкции:
- AutoSchema: по умолчанию схема выводится из первых объектов — «фабрика собирает комплектацию по первому заказу». Ошиблись в типах первых данных — живём с этим или переимпортируем. В проде задавайте схему явно
- Смена векторизатора или деприкейшн модели = полная пере-эмбеддировка. Это операция, а не флаг
- Мультитенантность включается при создании коллекции. После включения запросы обязаны передавать тенанта: неактивный вернёт ошибку с просьбой активировать, а не поиск по горячим данным. Это фича, но первый раз — сюрприз
- Python-клиенты v3 и v4 несовместимы: половина туториалов в сети на v3-синтаксисе, который в v4 не запустится (даже термины сменились: классы → коллекции). Ставим v4 (`pip install -U weaviate-client`), миграционный гайд — в доках
- alpha в гибриде: 0 — чистые векторы, 1 — чистый BM25 (ключевые слова). Не копируйте дефолт из туториалов — прогоните evals на своих запросах

**Цена владения:** бесплатно, BSD-3-Clause. Weaviate Cloud (serverless/enterprise) — managed, если не хочется строить сервисную зону самому. Embedded-режим — для локальных тестов и CI

**Механики и запчасти:** Weaviate B.V. (Амстердам), доки отличные, комьюнити активное. «Инженеров Weaviate» на рынке не больше, чем «инженеров Qdrant», но рулить реально бэкендеру

`✅` **Берите, если:** SaaS с кучей тенантов, нужен гибрид BM25+векторы без своего sparse-эмбеддера, хочется векторизацию и генерацию «под ключ» в одной базе
`❌` **Проезжайте мимо, если:** вся логика в SQL (универсал), счёт на миллиарды с GPU (поезд), либо ops-бюджет минимален — кроссовер в полной комплектации требует сервисной зоны

Тест-драйв:
```python
# weaviate-client v4: pip install -U weaviate-client
# embedded-режим скачает бинарники один раз; в проде — Docker или Weaviate Cloud
import weaviate
from weaviate.classes.config import Configure, Property, DataType
from weaviate.classes.query import Filter

client = weaviate.connect_to_embedded()

docs = client.collections.create(
    "Document",
    vectorizer_config=Configure.Vectorizer.none(),  # векторы приносим сами (по-хэтчбековски)
    properties=[
        Property(name="title", data_type=DataType.TEXT),
        Property(name="year", data_type=DataType.INT),
    ],
)

docs.data.insert(
    properties={"title": "Quarterly report 2024", "year": 2024},
    vector=embed("Quarterly report 2024"),  # embed() — ваша функция эмбеддингов
)

# гибрид: BM25F + векторы в одном запросе
# alpha = баланс: 0 — векторы, 1 — BM25; подберите на evals
res = docs.query.hybrid(
    query="annual financial summary",
    vector=embed("annual financial summary"),
    alpha=0.5,
    filters=Filter.by_property("year").equal(2024),
    limit=10,
)

for obj in res.objects:
    print(obj.uuid, obj.metadata.score, obj.properties["title"])
```

Кроссовер берёт не скоростью хэтчбека и не простотой самоката — он берёт комплектацией: целая фабрика RAG внутри одной базы. Платите вы не за руль, а за сервисную зону под опции.
